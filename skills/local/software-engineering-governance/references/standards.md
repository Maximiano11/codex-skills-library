# Referências verificadas em 22/10/2026

Os resumos abaixo descrevem finalidade; não reproduzem cláusulas nem criam obrigação
universal. Para avaliação normativa formal, obter acesso autorizado à edição
relevante e registrar cláusula, aplicabilidade e evidência. Preservar edição
contratada pelo projeto, mesmo quando houver versão mais recente.

| Fonte primária | Uso e limite |
| --- | --- |
| [ISO/IEC 25010:2011](https://www.iso.org/standard/35733.html) | Edição usada pelo artigo. O catálogo de 2023 a identifica como retirada. |
| [ISO/IEC 25010:2023](https://www.iso.org/standard/78176.html) | Modelo de qualidade de produto, nove características. Não é uma suíte de testes. |
| [ISO/IEC 25023:2016](https://www.iso.org/standard/35747.html) | Medidas de qualidade do produto. Não fixa limiares universais de aprovação; definir metas pelo sistema/necessidade. |
| [ISO/IEC/IEEE 12207:2026](https://www.iso.org/standard/90219.html) | Processos de ciclo de vida; catálogo consultado apresenta edição 2026, substituindo 2017. Não impõe uma metodologia específica. |
| [ISO/IEC/IEEE 29148:2018](https://www.iso.org/standard/72089.html) | Engenharia de requisitos e seus itens de informação. Havia revisão em andamento na consulta. |
| [ISO/IEC/IEEE 42010:2022](https://www.iso.org/standard/74393.html) | Descrição de arquitetura; não exige microserviços ou uma arquitetura determinada. |
| [OWASP ASVS 5.0.0](https://asvs.owasp.org/) | Requisitos verificáveis de segurança para aplicações/serviços web. Fonte consultada informa publicação em 30/05/2025. Registrar versão e identificador real ao selecionar requisito. |
| [OWASP Top 10:2025](https://top10.owasp.org/2025/0x00_2025-Introduction/) | Consciência/priorização de riscos; não substitui ASVS, modelo de ameaças ou testes. |

Não inventar números de requisitos ASVS ou cláusulas ISO. A implementação usa
controles operacionais próprios sem IDs normativos fictícios. Renovar a consulta
quando uma atualização normativa afetar a tarefa; não alegar que esta lista é
permanentemente a mais recente.

SOLID/DRY/KISS/YAGNI são heurísticas de projeto, ADR é um registro de decisão e
CI/CD é infraestrutura de integração/entrega. Aplicá-los por necessidade concreta,
sem atribuí-los como requisitos de certificação. Gates locais não substituem
proteção de branch, revisão humana ou autorização de produção.
